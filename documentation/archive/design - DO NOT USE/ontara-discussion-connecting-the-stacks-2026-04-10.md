## 1. The Starting Point

Stage 8 (the Ontara Portal) is complete. The portal is a convincing and well-structured prototype: it has user authentication, domain management, a 10-module catalogue (6 business, 2 generative, 2 analytical), two intersecting lifecycle state machines, schema-driven configuration, BMM-concern-structured domain context, module composition guidance, simulation with batch event generation and comparative analytics, progressive governance with typed constraint evaluation, a promotion path with prerequisite gating, and lifecycle governance guards.

What it does not have is any connection to anything real. The modules describe what a business does. Nothing makes the business do it. The simulation events are generated by random distributions, not produced by an executing system. The governance constraints are evaluated by typed functions, not by observing a live process. The portal is architecturally honest in its structure but operationally isolated.

The post-Stage-8 direction question is: what comes next, and what does "next" mean for a platform whose thesis is that a model generates and governs a running system?

The discussion began with a natural inclination to continue driving development from the front end — small steps toward something real executing — and quickly arrived at a more fundamental question.

---

## 2. The Four-Plus-One Things That Need to Connect

The discussion identified that there are at least five things that eventually need to talk to each other. They are currently isolated islands.

**1. The SysML model** — the single source of truth for what a service business is and how it works. Feeds the generation pipeline. Governs structure and semantics. Currently connected only to the console (via `model-introspection.json`) and the OWL pipeline (via the KG).

**2. The Console** — the developer/architect's view of the model. Reads `model-introspection.json`. Shows BMM structure, patterns, vocabulary, architecture, ontology. Purely a reading tool — it observes the model, it does not interact with running systems.

**3. The Portal** — the operator's view of a running domain. Currently standalone SQLite. Module definitions are hand-seeded and happen to use BMM concept names, but are not derived from the model. Architecturally, this is dishonest — the portal speaks the language of the BMM but is not connected to it.

**4. The execution layer** — where business processes actually run. For the cafe this means Temporal orchestrating the FulfilDrink workflow, XState managing drink lifecycle, EHRbase storing records, Postgres persisting state. Completely disconnected from the portal.

**5. The customer-facing UI** — where the service user interacts with the business. The coffee shop demonstrator has a hybrid developer/operator UI, not a genuine customer-facing UI. A customer kiosk — a separate SvelteKit application, touchscreen-style, through which a customer places an order — does not yet exist.

The key observation is that connection 1→2 (model to console, via the generation pipeline) is the only real connection that currently exists. Everything else is an isolated island. "Connecting everything" means building 1→3, 3→4, 5→4, and making the model the grounding truth for all of them.

---

## 3. Process Execution — The First Set of Options

Before arriving at the deeper architectural question, the discussion explored what the smallest useful step toward real process execution might look like within the portal as it stands. Four options were considered.

**Option A — Process step sequences within modules.** Extend ActivityModel modules so they can define a named sequence of steps. The portal tracks position in the sequence per case. No external orchestration; just SQLite-persisted step state. Lightest viable process execution — analogous in concept to FulfilDrink (take order → make drink → serve), but implemented entirely within the portal.

**Option B — Case management as entry point.** Introduce the concept of a "case" or "service episode" at the domain level. Cases have a subject, a current state, and progress through stages. Modules contribute their concern to a case. More architecturally interesting — it connects to ActivityModel and ServiceConcept, and begins to exercise the domain context model. A larger conceptual step.

**Option C — Task boards.** Each active module generates tasks; the dashboard shows a kanban board. Very lightweight, but too generic — doesn't exercise the architecture.

**Option D — Schema-to-form-to-data pipeline.** Extend the schema-driven configuration pattern so modules can also define operational data entry forms. Form responses become the beginnings of domain data. Interesting but about data capture rather than process execution.

The view reached was that Options A and B are the right territory, with C too generic and D serving a different purpose. Between A and B: A is more self-contained and deliverable in a few sessions; B is architecturally richer because it introduces the episode concept GSL will eventually need. A natural hybrid suggests itself — start with A (step sequences in ActivityModel modules), and let that naturally evolve toward B as the episode concept matures.

However, this set of options was superseded by the recognition that the portal's process execution question cannot be answered in isolation from the execution layer. The deeper question followed immediately.

---

## 4. The Real Question — When Does the Prototype Become the Thing?

The question was posed directly: at what point do we open a web frontend for an actual business, allow a real (or dummy) service user to interact with something being provided, and connect the portal to the existing running system — the model, the knowledge graph, Temporal, all of it?

This reframed the discussion from "what small feature should we add to the portal?" to "what is the gap between the portal as it stands and a portal that is operationally real?"

The coffee shop demonstrator is proof that a real running system can be generated from the model. SvelteKit frontend, Temporal workflows, EHRbase CDR, PostgreSQL — a real execution stack, driven by model-derived process definitions, with a hybrid operator/developer UI. The demonstrator works. The question is how to connect it to the portal's operator layer and to the model as a shared source of truth.

The gap between them is a bridge. The portal knows what business processes exist and how they are governed. The coffee shop knows how to execute a specific process. Neither knows about the other.

---

## 5. Clarifying the Paths to Connection

Three paths were proposed for closing the gap. An initial description conflated two of them, which was corrected in discussion.

**Path 1 — Portal as orchestration layer over execution engines.** The portal remains the operator's tool. When an ActivityModel module reaches the right lifecycle state, it connects to a Temporal workflow definition. The portal governs and observes; it does not execute. Module dashboards show live state from the execution layer. Events flow from Temporal to the portal. This is architecturally the cleanest path — it directly expresses the dual-stack architecture's intent. The portal is the governance and observation layer over real execution. The SMM right-hand stack is the execution side; L5 operational simulation is the SMM made live.

**Path 2 — Portal absorbs lightweight execution directly.** For simple processes, the portal implements step sequences directly in SQLite. A `case` table with a `current_step` column, transitions validated by the module's process definition. Reserve Temporal for complex orchestration. Faster to build; risks the portal becoming a mini workflow engine when a proper one already exists in the stack.

**Path 3 — Cafe as the concrete proving ground.** Take the existing coffee shop and connect it to a portal domain. Create a "Cafe" domain in the portal with its modules configured and promoted. Build the bridge: the portal's ActivityModel module connects to the existing FulfilDrink workflow. Orders appear in both places — the customer kiosk for ordering, the portal for the operator's view. This is concrete-first: let the general interface emerge from the specific case.

The key clarification reached was that Paths 1 and 3 are not different destinations — they are the same destination approached differently. Path 1 describes the general interface; Path 3 describes the concrete instantiation that should reveal the general interface. Given Ontara's methodology — cross-domain validation, validate in toy domains first, co-evolution — the approach is obviously to start from the concrete. The cafe is the toy domain. It is already running. Path 3 is how you build Path 1.

Path 2 was set aside. It risks architectural dishonesty — building a workflow engine inside the portal when Temporal already exists and is already proven.

**The agreed direction** is Path 3 leading to Path 1: connect the existing coffee shop execution layer to a real portal domain, prove the architecture with working code, and let the general portal-to-execution interface emerge from that.

## 6. A Critical Architectural Clarification — Two Distinct Runtime States

The most architecturally significant moment in the discussion was a clarification proposed by Ella about what the dual stack actually means at runtime. This is worth capturing with precision.

The dual stack is not two views of the same data from different angles. It is two genuinely distinct things happening simultaneously, each with its own state, each changing as a result of a service episode.

**On the SMM side (system runtime state):** a workflow instance transitions through states. Resources are consumed and released. Data is written to the execution database. The infrastructure does its work. At the end of the episode, the workflow instance terminates. The execution infrastructure returns to its resting state — ready to receive the next instance. The instance is gone; the system retains operational history (logs, metrics, performance records). The cumulative state of the SMM at any moment is: the set of active workflow instances, the queue depths, the processing times, the resource utilisation.

**On the BMM side (business runtime state):** a customer received value. The business received revenue. Inventory decreased. The daily order count incremented. Cumulative sales increased. A loyalty record may have been updated. The customer's relationship with the business may have deepened. These are business-level facts that persist beyond the episode and accumulate over time. The business is meaningfully different after the transaction than before it — not in the sense that the workflow has changed, but in the sense that the business's position in its operating environment has changed.

These are not the same data. The workflow execution does not know about daily sales totals — that is a BMM concern. The business model does not know about workflow instance IDs — that is an SMM concern. But when the workflow completes an order, both states change, each in their own terms.

**The horizontal mappings at runtime level are the rules that keep both sides synchronised.** When the FulfilDrink workflow reaches the Delivered state, the mapping rule says: increment the business model's daily order count and add the order total to daily revenue. The mapping is the bridge that makes the BMM-side state change as a consequence of the SMM-side state change. Without the mapping, the two sides drift apart — the execution layer knows orders completed, but the business model doesn't know the business grew.

**Consequence for what the portal must show.** The operator's dashboard needs to display both sides. "23 orders in progress" is an SMM fact — sourced from the Temporal workflow engine. "127 orders served today, £412 revenue" is a BMM fact — sourced from the business state store. These require different data sources, different query paths, and different update mechanisms. A portal that shows only SMM state is showing the system. A portal that shows only BMM state is showing the business. The operator needs both.

## 7. Shared Infrastructure, Strict Model Bindings

A further architectural clarification settled an important question about implementation: the infrastructure used on both sides of the stack does not need to be different. The same tools and frameworks can appear on both sides.

SvelteKit does not care whether it is rendering a BMM dashboard or an SMM workflow monitor. SQLite does not care whether it is storing daily sales totals or workflow instance state. Temporal could orchestrate business-level processes as well as system-level ones.

**What is not neutral is the binding between a piece of infrastructure and the model.** A given Temporal workflow definition is either implementing an SMM process or a BMM process. A given database table either holds SMM state or BMM state. Every piece of running infrastructure must explicitly declare which side of the stack it belongs to, and its structure must be governed by the model element it implements.

The discipline is not "use different tools for each side" — it is: every piece of running infrastructure declares its model binding, and that binding is authoritative for the structure and semantics of the infrastructure element. A SvelteKit route, a database table, a Temporal workflow definition — all should carry metadata (in a manifest, in frontmatter, in a configuration file) that says which model element they implement and which side of the stack that element belongs to.

This is A3 (model generates everything) and A1 (separation of representation and execution) expressed at the level of deployment infrastructure rather than just code generation. And it means the generation pipeline eventually needs to reach further — not just generating console data and OWL vocabulary, but generating the binding declarations that keep the runtime infrastructure tethered to the model.

## 8. Positions Reached

The following positions were reached in discussion and should be treated as the starting commitments for Stage 9 planning.

**S192-D1.** The post-Stage-8 direction is to connect the existing isolated islands — model, console, portal, execution layer, and customer-facing UI — into a coherent, model-grounded system. The direction is not to add more prototype features to the portal in isolation.

**S192-D2.** The current approach to immediate progress is concrete-first: e.g. use the existing coffee shop demonstrator as the connecting medium. The cafe is a running system. The portal exists. The model governs both in principle but neither in practice. The first move is to make that governance real by connecting them.

**S192-D3.** Path 2 (portal absorbs lightweight execution directly in SQLite) is set aside. It risks architectural dishonesty and duplicates capability that already exists in the Temporal-based execution stack.

**S192-D4.** The SMM runtime state (workflow execution, queue depths, operational metrics) and the BMM runtime state (business facts, cumulative measures, revenue, inventory) are architecturally distinct. They require separate stores, separate update paths, and separate query mechanisms. Both must be visible to the portal operator.

**S192-D5.** The horizontal mappings at runtime level are the rules that update BMM state as a consequence of SMM state changes (episode completion events). These mappings are as much a part of the architecture as the dual-stack description itself.

**S192-D6.** Shared infrastructure is acceptable and expected on both sides of the stack. The discipline is strict model binding: every piece of runtime infrastructure declares which model element it implements and which side of the stack that element belongs to.

**S192-D7.** The portal's module catalogue must be derived from the SysML model (via `model-introspection.json` or equivalent) rather than hand-seeded in SQLite. This is the foundational honesty requirement — without it, the portal speaks the language of the BMM but is not connected to it.

**S192-D8.** A customer ‘kiosk UI’ for the cafe is a genuine deliverable — a separate SvelteKit application, touchscreen-style, through which a dummy customer places an order. This is not cosmetic. It exercises the SMM's customer-facing execution path and provides the source of SMM events that the portal will observe.

## 9. Open Questions

The following questions were surfaced during the discussion and were not fully resolved. They are the agenda for further exploration before a Stage 9 plan can be finalised.

**Q1 — Where does BMM runtime state live?** The discussion established that BMM state is distinct from SMM state and must have its own store. But where? Options: a dedicated table in the portal's SQLite database (making the portal the owner of business facts); a separate service or database that both the portal and other BMM tools can query; the knowledge graph (OWL triple store, already the canonical representation of the BMM's structural vocabulary). The KG is the most architecturally coherent answer — it is already the canonical BMM store — but adding *runtime instance data* to the KG (daily order counts, revenue totals) is different from the KG's current role as a vocabulary and structural store. This warrants its own design discussion.

**Q2 — How are the horizontal mappings implemented?** The mappings that update BMM state when SMM episodes complete are architecturally described (they exist in principle as the dual-stack's connecting layer) but not yet implemented in any form. What is the implementation pattern? Options: event handlers in the Temporal workflow that write directly to the BMM store on workflow completion; a separate mapping service that subscribes to Temporal workflow events and applies mapping rules; mapping rules expressed in the SysML model and generated as code. The third option is architecturally the richest (A3) but also the most ambitious.

**Q3 — What does "module derived from model" actually mean at the data level?** S192-D7 says the portal's module catalogue must derive from the model. But the portal's modules are currently richer than what `model-introspection.json` provides — they have lifecycle state machines, governance constraints, configuration schemas, composition hints. Which of these are generated from the model (and how?), which are portal-native (authored in the portal, stored in SQLite), and which should be in neither place but derived from the OWL vocabulary? The boundary between model-generated structure and portal-native operational state needs to be drawn explicitly before implementing D7.

**Q4 — What is the scope of the customer kiosk?** The kiosk is described as a separate SvelteKit application that places orders into the Temporal workflow. But what exactly does "placing an order" involve? Does the kiosk communicate directly with Temporal (via an API), or does it go through an intermediary (an order service, or the portal itself acting as an orchestration layer)? And does the kiosk need to show order progress (the SMM tracking the workflow) or just accept the order and let the operator's portal show what happens next?

**Q5 — What is the connection sequence and what does each step prove?** The discussion proposed a rough ordering: (1) model → portal (module catalogue derived from model), (2) customer kiosk UI, (3) portal observes execution. But this needs to be made precise in terms of what architectural thesis each step tests, what the acceptance criterion is, and whether the order is right. In particular: should the portal observe the execution layer (step 3) before or after the kiosk exists (step 2)? You can build the event feed from Temporal to the portal without a kiosk, using the existing hybrid coffee shop UI to generate orders. Step 2 might be later in the sequence than it initially appeared.

**Q6 — Console integration.** The console currently shows the developer/architect's view of the model. In a connected system, the console would also need to show something about what is running — not the operator's view (that is the portal) but the architect's view of how the running system relates to the model. What does that look like? Is it a new console view that shows "which model elements have live infrastructure bound to them"? This is a lower-priority question but deserves a position before Stage 9 planning finalises.

**Q7 — The Portal-to-Console relationship.** The portal and console are currently completely separate applications that happen to share the BMM vocabulary. In a model-grounded system, an operator making a configuration change in the portal should be doing something that is traceable back to the model the architect sees in the console. How tight should this traceability be? And if the portal's module catalogue is derived from the model, what happens when the model changes — does the portal automatically update, does the operator re-derive, or does a mismatch trigger a governance alert?
