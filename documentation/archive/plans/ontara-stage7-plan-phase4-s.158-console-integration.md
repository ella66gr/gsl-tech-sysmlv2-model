## 1. Context and Scope

Stage 7 Phases 1–3 are complete. The reasoning vocabulary (`ontara-reasoning.ttl`) now stands at 42 classes, 15 named individuals, 40 object properties, 10 datatype properties, with 56/56 SPARQL queries passing and HermiT CONSISTENT across a 12-file ontology stack. The vocabulary covers:

- Core reasoning classes (context, goals, obstacles, measures, decisions, plans)
- Three-way constraint hierarchy (HardConstraint, SoftConstraint, GradedRule)
- Evidence architecture (SEPIO pattern: Claim → EvidenceLine → EvidenceItem)
- Structured probabilistic reasoning types (BayesianUpdater, RiskCalculator, PrognosticModel, PredictiveAnalytics)
- Decision mode routing (DecisionMode, four Cynefin domain individuals)
- Heuristic packs (HeuristicPack, 4 heuristic subtypes, pack composition properties)
- Constraint satisfaction extensions (semiring properties, truth-value ranges, composition)
- STAMP/STPA safety structures (SafetyConstraint, ControlStructure, ControlLoop, ControlAction, UnsafeControlAction)
- FRAM-ready slots (FRAMFunction, VariabilityProfile)
- Governance alignment (Obligation and Prohibition as HardConstraint subclasses)
- PROV-O dual subclassing (4 classes with BFO + PROV-O parentage)

Phase 4 makes this vocabulary visible in the Ontara Console, fulfilling the co-evolution commitment (J2): no modelling without the tool that makes it legible.

## 2. What Phase 4 Is Not

The following are explicitly **out of scope:**

- **Populated reasoning instances in the console.** The reasoning vocabulary defines the schema (classes, properties, individuals for interpretive frames and Cynefin domains). There are currently no domain-specific reasoning *instances* in the knowledge graph (e.g. no Cafe triage decisions, no Suds COSHH claims). Console views that require instance data — such as browsing specific evidence chains or tracing specific decisions — would show empty panels. Phase 4 focuses on making the **vocabulary structure** visible and navigable.

- **New SPARQL-backed live query views.** The console reads from static JSON (`model-introspection.json`, `reasoning-summary.json`). It does not query GraphDB directly. Phase 4 continues this pattern. Live SPARQL integration remains a future workstream (Stage 5 Phase 4).

- **Runtime reasoning engine integration.** Per B29 and the Stage 7 scope boundary — runtime engines are deployment-time concerns.

## 3. Current Console State

The Ontology view (`/ontology`) currently has two sections:

1. **Ontological Hierarchy** — a collapsible BFO→CCO/IAO→BMM tree showing how the 34 BMM elements map to BFO classes via mid-level ontologies. BMM leaf nodes link to the Glossary. Data source: `model-introspection.json` → `ontologicalHierarchy` (generated by `gen_model_introspection.py`).

2. **Knowledge Graph Status** — five stat cards (consistency, ontology file count, typed relationships, weighted relationships, OWL classes), an expandable ontology stack table, and an object properties table. Data source: `reasoning-summary.json` (generated by `reason_kg.py --save-summary`).

**Current problem:** The reasoning summary JSON in the console's static data directory is stale — it shows 10 files and 34 domain classes, but the current stack is 12 files with 42+ reasoning classes, 15 named individuals, 40 object properties, and 10 datatype properties. The stats do not reflect Phases 1–3.

## 4. What Has Changed Since the Stage 7 Plan Was Written

The Stage 7 plan §7 was written at Session 148, before any Phase implementation. It described three high-level deliverables:

| Plan §7 item | Assessment now |
|---|---|
| **P4-1: Reasoning explorer view** | Appropriate, but the scope should focus on the vocabulary *structure* (class hierarchy, property declarations, named individuals), not on browsing instance data (which does not exist) |
| **P4-2: Evidence browser** | Premature. The evidence architecture classes exist, but there are no Claim/EvidenceLine/EvidenceItem instances in the knowledge graph. This view would show an empty shell. More appropriate when domain-specific reasoning instances are populated (future workstream) |
| **P4-3: Decision trace visualisation** | Premature for the same reason. Decision traces require populated ReasoningActivity → Decision → Claim chains. No such data exists yet |

**Revised assessment:** Phase 4 should deliver one substantive new capability — the reasoning vocabulary explorer — and extend the existing KG Status panel to reflect the full 12-file stack. The evidence browser and decision trace views should be deferred to a future phase when instance data exists, consistent with J2 (co-evolution: no tool without model content that exercises it).

## 5. Revised Phase 4 Scope

### 5.1 Prerequisite: Regenerate reasoning summary

Before any console work, `reason_kg.py --save-summary` must be run and the output copied to the console static data directory. This brings the KG Status panel up to date immediately with no code changes.

### 5.2 Update KG Status panel

Extend the KG Status panel to show the full picture of the ontology stack:

- **New stat cards:** Named individuals count, datatype properties count, SPARQL query count — these are now significant metrics that the current panel omits.
- **Updated stats:** The existing stat cards (ontology file count, object properties, domain classes) will automatically update when the regenerated summary is loaded.
- **Vocabulary module breakdown:** A new sub-panel showing the composition of the ontology stack by module (BMM, governance, domain, reasoning, axioms, imports) with class/property counts per module.

### 5.3 Reasoning Vocabulary Explorer

A new section on the Ontology page (or a separate sub-route `/ontology/reasoning`) showing:

- **Reasoning class hierarchy tree** — following the same collapsible tree pattern as the BFO hierarchy, but showing the `ontara-rsn:` class structure. Root nodes: the major groupings (foundation classes, core reasoning, evidence architecture, probabilistic types, constraint hierarchy, safety/resilience, FRAM). Leaf nodes show the class name, label, parent class(es), and comment.
- **Object properties table** — the 40 reasoning object properties with domain, range, and OWL characteristics. Follows the existing object properties table pattern but for `ontara-rsn:` properties specifically.
- **Named individuals panel** — the 15 named individuals (3 interpretive frames, 4 Cynefin domains, 8 heuristic subtypes) with their type and label.
- **Cross-module connections** — visual indicators showing where the reasoning vocabulary connects to other modules (governance alignment: Obligation/Prohibition as HardConstraint subclasses; PROV-O dual subclassing).

### 5.4 Data pipeline extension

The reasoning summary JSON needs to be extended to include the data the new views require. Currently `reason_kg.py --save-summary` produces basic stats. It needs to additionally extract:

- Class hierarchy (parent–child relationships) for `ontara-rsn:` classes
- Named individuals with their types
- Datatype properties
- Cross-module subclass axioms

This is an extension to `reason_kg.py`, not to `gen_model_introspection.py` — the reasoning vocabulary is OWL-authoritative (B29), not SysML-derived.

## 6. Implementation Steps

### Step 4.0: Regenerate reasoning summary [Code]

**Objective:** Bring the console's static data files up to date.

**What to do:**
1. Run `python3 scripts/reason_kg.py --save-summary`
2. Copy `generated/ontara/reasoning-summary.json` to `console/static/data/reasoning-summary.json`
3. Verify the stat cards update correctly in the console

**Acceptance criteria:** KG Status panel shows 12 ontology files, updated class count (reflecting reasoning classes), updated object property count.

**Tag:** `[Code]`

### Step 4.1: Extend reasoning summary data [Code]

**Objective:** Add class hierarchy, named individuals, datatype properties, and cross-module axiom data to the reasoning summary JSON.

**What to do:**
1. Extend `reason_kg.py`'s `--save-summary` output to include a new `reasoningVocabulary` section:
   - `classes`: list of `{iri, label, comment, parents: [iri], module}` for all `ontara-rsn:` classes
   - `namedIndividuals`: list of `{iri, label, types: [iri]}` for all `ontara-rsn:` named individuals
   - `objectProperties`: list of `{iri, label, domain, range, characteristics: [], comment}` for `ontara-rsn:` properties
   - `datatypeProperties`: list of `{iri, label, domain, range, comment}` for `ontara-rsn:` properties
   - `crossModuleAxioms`: list of `{subject, predicate, object, description}` for cross-module subclass declarations
   - `moduleSummary`: `{classCount, objectPropertyCount, datatypePropertyCount, namedIndividualCount, sparqlQueryCount}`
2. The extraction should use SPARQL queries against GraphDB (or rdflib parsing of the Turtle file directly) to keep the data source OWL-authoritative
3. Regenerate and copy to console static data

**Acceptance criteria:** `reasoning-summary.json` includes `reasoningVocabulary` section with all fields populated. Data is accurate against the Turtle file.

**Tag:** `[Code]`

### Step 4.2: Update TypeScript types [Chat]

**Objective:** Extend the Ontology view type definitions to accommodate the new data.

**What to do:**
1. Add new interfaces to `console/src/lib/types/ontology.ts`:
   - `ReasoningClass` (iri, label, comment, parents, module)
   - `ReasoningNamedIndividual` (iri, label, types)
   - `ReasoningDatatypeProperty` (iri, label, domain, range, comment)
   - `CrossModuleAxiom` (subject, predicate, object, description)
   - `ReasoningModuleSummary` (counts)
   - `ReasoningVocabulary` (classes, namedIndividuals, objectProperties, datatypeProperties, crossModuleAxioms, moduleSummary)
2. Extend `ReasoningSummary` to include `reasoningVocabulary?: ReasoningVocabulary`
3. Extend `ReasoningStats` to include `namedIndividualCount`, `datatypePropertyCount`, `sparqlQueryCount`

**Acceptance criteria:** Types compile cleanly. Page loader accepts the extended JSON.

**Tag:** `[Chat]` (small, targeted edits via MCP)

### Step 4.3: Update KG Status panel [Code]

**Objective:** Extend the stat cards and add the vocabulary module breakdown.

**What to do:**
1. Add stat cards for: named individuals count, datatype properties count, SPARQL query count
2. Add a "Vocabulary Modules" collapsible sub-panel below the ontology stack table, showing per-module breakdowns (imports, BMM pipeline, BMM axioms, governance, domain, reasoning) with class/property/individual counts for each
3. Follow existing Flowbite Svelte patterns for card layout and expansion

**Acceptance criteria:** All new stat cards render correctly. Module breakdown panel shows accurate per-module counts. Existing functionality preserved.

**Tag:** `[Code]`

### Step 4.4: Build reasoning vocabulary explorer [Code]

**Objective:** Build the primary Phase 4 deliverable — the reasoning vocabulary explorer.

**What to do:**
1. Add a new section to the Ontology page below the KG Status panel (or as a separate collapsible panel), titled "Reasoning Vocabulary"
2. **Class hierarchy tree:** Collapsible tree showing the `ontara-rsn:` class structure. Group by functional area:
   - Foundation (ReasoningActivity, Claim, ReasoningAgent, Decision)
   - Core Reasoning (ReasoningContext, ReasoningComponent, Goal, Obstacle, Measure, Plan)
   - Constraints (Constraint → HardConstraint, SoftConstraint, GradedRule)
   - Evidence (EvidenceLine, EvidenceItem, ConfidenceAssessment)
   - Probabilistic (StructuredProbabilisticComponent → BayesianUpdater, RiskCalculator, PrognosticModel, PredictiveAnalytics)
   - Knowledge & Heuristics (KnowledgeSource, Heuristic → subtypes, HeuristicPack, DecisionMode)
   - Safety & Resilience (SafetyConstraint, ControlStructure, ControlLoop, ControlAction, UnsafeControlAction, FRAMFunction, VariabilityProfile)
3. Use visual styling consistent with the BFO hierarchy — different tier colours for grouping nodes vs. class nodes
4. Each class node shows: label, IRI suffix, parent class(es), and truncated comment on expand
5. **Named individuals panel:** Grid or list of the 15 named individuals with type badge
6. **Properties tables:** Two tables (object properties, datatype properties) following the existing object properties table pattern
7. **Cross-module connections:** Badge indicators on classes that have cross-module subclass relationships (e.g. "← ontara-gov:Obligation" on HardConstraint)

**Acceptance criteria:** All 42 reasoning classes visible in the hierarchy. All 15 named individuals displayed. All properties listed with domain/range. Cross-module connections indicated. Navigation state preserved via NavigationStore.

**Tag:** `[Code]`

### Step 4.5: Navigation registration [Chat]

**Objective:** Register the reasoning vocabulary explorer with the global navigation context (I19).

**What to do:**
1. If the reasoning explorer is a separate sub-route, register it with the NavigationStore
2. Ensure breadcrumb trail works correctly (Ontology → Reasoning Vocabulary)
3. Add the route to the console's navigation sidebar if appropriate

**Acceptance criteria:** Navigation state capture and restore works. Breadcrumbs display correctly.

**Tag:** `[Chat]` (targeted edit if same page) or `[Code]` (if new route)

### Step 4.6: Validation and cleanup [Code]

**Objective:** End-to-end verification.

**What to do:**
1. Verify all data renders correctly against the current 12-file ontology stack
2. Check dark mode rendering
3. Verify no console errors
4. Ensure `model-introspection.json` and `reasoning-summary.json` are both current in console static data

**Acceptance criteria:** Console builds clean. All views render correctly in light and dark mode. No console errors.

**Tag:** `[Code]`
