## 1. Scope and Objectives

Phase 3 has two objectives:

1. **Complete the consolidation that Phase 2 deferred.** The SPARQL validation suite was not extended to cover Phase 2 axiom types (deferred success criterion 6). The live reasoning summary has been carried forward since Session 120. The governance vocabulary extensions designed in Session 132 have not been implemented. These are debts — Phase 3 pays them.

2. **Build the round-trip diff engine.** This is Pipeline Stage 5 from the KG architecture paper §12 — the ability to compare generated OWL against the live triple store, detect discrepancies, and report them in a structured format. This is the prerequisite for any future OWL→SysML patch generation and is the single most important new pipeline capability for Phase 3.

Phase 3 follows the same Block A/B sequencing that worked in Phase 2: Python/OWL depth work first, then a second block that extends the pipeline. Both blocks stay within the KG engineering domain — no console work in this phase.

---

## 2. What Phase 3 Is Not

The following are explicitly **out of scope** for Phase 3:

- **Live SPARQL console integration** (querying GraphDB at runtime from the console). This is Phase 4 work — a significant architectural change requiring design discussion before implementation.
- **Incremental graph updates** (replacing full-wipe-and-reload). Useful but not blocking — the current reload approach works at the current triple count (~30k). This becomes important only when the graph grows significantly (100k+ triples) or when round-trip patching needs targeted updates.
- **Formalising Regulation 17.** The governance vocabulary extensions (Step 3) add the schema properties. Populating them with Regulation 17 individuals is domain modelling work that belongs in the governance workstream, not the KG infrastructure phase. Phase 3 provides the vocabulary; a subsequent session or workstream provides the content.
- **Console changes.** Phase 3 is pure Python/OWL pipeline work.
- **Ears demonstrator design** ([[ontara-ref-work-items|W-015]]). Separate workstream.

### Step 3: Governance vocabulary extensions [Chat + Code]

**Objective:** Implement the 5 new object properties and 1 new data property specified in the [[ontara-discussion-governance-granularity-and-cross-references-2026-04-04|governance granularity paper]] §6.

**What to add to `ontology/governance/ontara-governance.ttl`:**

| Property | Type | Domain | Range | Characteristics |
|---|---|---|---|---|
| `crossReferencesRegulation` | Object | `DeonticDirective` | `DeonticDirective` | Symmetric (S135-D1) |
| `qualifiedBy` | Object | `DeonticDirective` | `DeonticDirective` | Not symmetric |
| `crossReferencesInstrument` | Object | `NormativeInstrument` | `NormativeInstrument` | Not symmetric |
| `amendsInstrument` | Object | `NormativeInstrument` | `NormativeInstrument` | Not symmetric |
| `supersedesInstrument` | Object | `NormativeInstrument` | `NormativeInstrument` | Not symmetric |
| `crossReferenceNote` | Data | `DeonticDirective` | `xsd:string` | — |

**Implementation approach:**
1. [Chat] Review the current `ontara-governance.ttl` property declarations for style consistency.
2. [Code] Add the 6 new property declarations to `ontara-governance.ttl`, following the existing declaration pattern (labels, comments, domain, range, characteristics).
3. [Code] Reload into GraphDB and run Robot + HermiT to confirm consistency.
4. [Code] Add SPARQL validation queries to `validate_kg.py` for the new properties.
5. [Code] Run full validation suite — all queries pass.

**Acceptance criteria:** 6 new properties declared. 10-file ontology stack remains CONSISTENT under HermiT. New SPARQL queries confirm property declarations. Governance object property count rises from 20 to 25; data property count from 16 to 17.

**Design decisions:**

**S135-D1: `crossReferencesRegulation` symmetry.** The governance granularity paper left this as S132-Q1. We resolve it here: **symmetric**. The pragmatic argument wins — if Regulation 12(2)(h) references the Hygiene Code provisions and we model `reg12-2h crossReferencesRegulation hygieneCodeCriterion1`, the inverse should be automatically available for queries like "what references this criterion?" Without symmetry, every cross-reference would need to be asserted twice. The one-directional nature of legislative drafting ("Reg 12 says 'subject to Reg 22'" but Reg 22 doesn't say "applies to Reg 12") is a feature of the source text, not of the semantic relationship — the *cross-reference relationship itself* is symmetric even if the *textual mention* is not.

**S135-D2: Vocabulary extensions are schema-only for now.** Per S132-D6, the properties are declared without instances. They become exercised when the next regulation (likely Regulation 17) is formalised in a subsequent workstream. This respects the boundary between infrastructure work (Phase 3) and content work (governance workstream).

**Estimated effort:** 1 session.

## 4. Block B — Round-Trip Foundation

### Step 4: Round-trip diff engine — design [Chat]

**Objective:** Design the diff engine that compares SysML-generated OWL against the live triple store and reports discrepancies.

**What to design:**
1. **Comparison scope.** What is compared? The pipeline produces `ontara-bmm.ttl`, `ontara-bmm-properties.ttl`, `ontara-bmm-weights.ttl`, and `ontara-correspondence.ttl`. Hand-authored files (`ontara-bmm-axioms.ttl`, `ontara-governance.ttl`, `cqc-reg12-individuals.ttl`) are OWL-authoritative and should not be compared against SysML-generated output — they have no SysML source to diff against. The diff operates within the SysML-authoritative and shared-constrained authority zones ([[concept-authority-zones|B29]]).
2. **Comparison granularity.** Triple-level diff is too noisy (blank node identity, serialisation order). The right level is *semantic unit* — a class declaration (IRI + label + comment + definition + parent), a property declaration (IRI + domain + range + characteristics), a weight individual (IRI + source + target + strength + rationale), a mapping record. Each semantic unit is compared as a whole.
3. **Diff categories.** What kinds of discrepancies can occur? At minimum: *added* (in generated, not in store), *removed* (in store, not in generated), *modified* (in both, but properties differ), *unchanged*.
4. **Output format.** Structured report — JSON or Markdown — suitable for both human review and future automated patching.
5. **Authority zone awareness.** The diff engine must know which triples are SysML-authoritative (pipeline-generated) and which are OWL-authoritative (hand-authored). It should only flag discrepancies in the SysML-authoritative zone — changes in the OWL-authoritative zone are expected and legitimate.

**Open questions for this step:**
- **S135-Q1:** Should the diff engine read from GraphDB via SPARQL, or from the Turtle files on disk? SPARQL queries the materialised state (including inferred triples); file comparison is simpler but misses inference. Recommendation: compare generated files against a SPARQL extract of the asserted content in the relevant named graphs, excluding inferred triples (consistent with the GraphDB finding S106-F2 — inferred triples are in the default graph, not named graphs).
- **S135-Q2:** Should the diff engine be a standalone script or integrated into `gen_owl_pipeline.py`? A standalone script (`diff_kg.py`) is cleaner — it has a different lifecycle (run after generation, not during) and a different dependency profile (needs GraphDB access).

**Deliverable:** Design document (discussion paper or plan section) specifying the diff engine architecture, comparison units, output format, and authority zone rules.

**Estimated effort:** 1 session (discussion).

### Step 5: Round-trip diff engine — implementation [Code]

**Objective:** Implement `scripts/diff_kg.py` per the design from Step 4.

**Implementation approach:**
1. [Code] Create `scripts/diff_kg.py` with `rdflib` for Turtle parsing and `urllib` for SPARQL queries against GraphDB.
2. [Code] Implement semantic unit extraction: parse pipeline-generated Turtle files into semantic units (class declarations, property declarations, weight individuals, mapping records).
3. [Code] Implement GraphDB extraction: SPARQL queries to extract the equivalent semantic units from the live store (asserted content only, from named graphs).
4. [Code] Implement comparison logic: match by IRI, compare property sets, classify as added/removed/modified/unchanged.
5. [Code] Implement reporting: structured output (JSON for machine consumption, Markdown summary for human review).
6. [Code] Test with the current state (should show zero discrepancies if GraphDB is freshly loaded from the pipeline output). Then introduce a deliberate discrepancy (e.g. edit a label in GraphDB) and verify the diff catches it.

**Acceptance criteria:**
- `python3 scripts/diff_kg.py` produces a clean report when GraphDB matches the pipeline output.
- Deliberate discrepancies are detected and correctly classified.
- OWL-authoritative content (hand-authored axioms, governance vocabulary) is excluded from the diff.
- Output includes both JSON and human-readable summary.

**Estimated effort:** 2–3 sessions.

## 6. Design Decisions

| ID | Decision | Rationale |
|---|---|---|
| S135-D1 | `crossReferencesRegulation` is symmetric | Resolves S132-Q1. The cross-reference relationship is semantically bidirectional even when the legislative text mentions it in only one direction. Avoids requiring every cross-reference to be asserted twice. |
| S135-D2 | Vocabulary extensions are schema-only (no instances) | Respects the boundary between infrastructure (Phase 3) and content (governance workstream). Properties are declared and validated; instances are created when the next regulation is formalised. Per S132-D6. |
| S135-D3 | Diff engine is a standalone script (`diff_kg.py`) | Separate lifecycle from generation pipeline. Different dependency profile (needs GraphDB). Clean separation of concerns: generate → load → diff → (future: patch). |
| S135-D4 | Diff operates at semantic unit level, not triple level | Triple-level diffs are noisy (blank nodes, serialisation order, datatype formatting). Semantic units (class declarations, property declarations, weight individuals) are the meaningful comparison granularity. |
| S135-D5 | Diff is authority-zone-aware | Only flags discrepancies in SysML-authoritative content ([[concept-authority-zones|B29]]). OWL-authoritative content (hand-authored axioms, governance vocabulary) is excluded — changes there are expected and legitimate. |

## 10. Risks and Mitigations

| # | Risk | Likelihood | Mitigation |
|---|---|---|---|
| R1 | SPARQL extraction from GraphDB doesn't cleanly match pipeline-generated Turtle due to serialisation differences | Medium | Compare at semantic unit level (S135-D4), not triple level. Normalise IRIs and literal formatting before comparison. |
| R2 | Blank node identity makes diff unreliable for restriction axioms | Medium | Restriction axioms are in `ontara-bmm-axioms.ttl` (OWL-authoritative) — excluded from the diff by S135-D5. If SysML-authoritative content later includes restrictions, blank node handling will need design work. |
| R3 | Governance property declarations create HermiT warnings or inconsistencies when combined with existing axioms | Low | Properties are additive with no cardinality restrictions. Domain and range declarations are compatible with existing class hierarchy. Validated by reasoner run in Step 3. |
| R4 | The 23-query SPARQL suite takes too long to run | Low | Current 10-query suite runs in seconds. Even at 25+ queries, SPARQL validation over ~30k triples is fast. |
| R5 | Diff engine scope creep — temptation to build the patch generator during Phase 3 | Medium | Explicit scope boundary: Phase 3 builds the diff (read-only comparison). Patch generation is Phase 5 or later. The diff output format should be designed to support future patching, but no patch code is written. |
